# AI 个人档案 · ai-personal-profile

> 一份可以被任何 AI 直接读取的「我」——跨模型、跨工具共享的个人上下文档案。
> 目的是：换一个 AI 对话时，不用从头自我介绍。

**仓库定位**

- 这是**事实档案**，不是简历美化稿：写真实情况，包括局限、偏好、雷区。
- 面向「机器读取」优化：短句、结构化、可被单条引用，避免长段落抒情。
- 单一可信来源：所有 AI 助手都应把这里的描述当作对我的默认认知，除非我另行说明。

---

## 使用说明

**给 AI 的读取建议**

1. 先读「个人简介与背景」建立基本认知，再读「沟通风格偏好」调整表达方式。
2. 「常用工具与技术栈」用于判断回答的技术深度与默认技术选型。
3. 与本仓库内容冲突时，以我当前对话中的明确指令为准。

**给我的更新原则**

- 一次提交只改一个章节，commit message 写清改了什么（便于 `git revert` 精准回退）。
- 新增事实直接写；不确定的写 `待确认`，不要编。
- 每季度回看一次「长期目标」，过期的挪到「历史目标」。

## 2. 工作与学习习惯

**节奏（示例条目）**

- 示例：上午 9:00–11:30 是深度工作时间，会议尽量排在下午。

**学习方式（示例条目）**

- 示例：学新东西先跑通最小示例，再看文档细节，最后读源码。

## 3. 沟通风格偏好

**整体偏好（示例条目）**

- 示例：先给结论，再给理由；不要用「首先/其次/最后」铺垫三段才进入正题。
- 示例：可以直接指出我的错误，不需要缓冲语，节省双方时间。
- 示例：不确定的地方请标注「不确定」，不要为了完整性编造细节。

**格式偏好（示例条目）**

- 示例：列表 > 长段落；关键数字和结论加粗。
- 示例：代码给完整可运行片段，不要只给伪代码或「省略若干行」。
- 示例：超过 5 步的操作，给编号步骤。

**明确不喜欢的（示例条目）**

- 示例：过度共情的开场（「这个问题问得非常好」）。
- 示例：含糊的「建议进一步优化」，希望能具体到改哪一行。
- 示例：反复确认同一件事。

**语言（示例条目）**

- 示例：中文为主，技术名词保留英文原文（如 deployment、latency）。
- 示例：正式文档用中文书面语，聊天场景可以口语化。

## 5. 项目经验与成果

> 每个项目按「背景 → 我做了什么 → 结果 → 沉淀」记录，结果尽量带数字。

**项目模板**

```text
项目名称：
时间：
我的角色：
背景与问题：
关键动作：
结果（可量化）：
沉淀（代码 / 文档 / 方法论）：
```

**示例条目**

- 示例：**订单对账自动化**
  - 背景：人工核对 3 个系统的订单差异，每周约 6 小时。
  - 动作：写 Python 脚本拉取三方数据，做差异比对并生成异常清单。
  - 结果：核对时间从 6 小时降到 20 分钟，漏单率降到 0。
  - 沉淀：脚本进了团队仓库，被 2 个小组复用。

- 示例：**内部知识库迁移**
  - 背景：散落在 4 个工具里的文档无人维护。
  - 动作：设计目录规范 + 批量迁移 + 写归档规则。
  - 结果：文档检索平均耗时从 5 分钟降到 1 分钟。

## 待办与跟踪

本仓库用 **Issues** 作为待办池，规则如下：

- 每个待填充章节对应一个 Issue，标题前缀 `[档案]`。
- 新增想法先开 Issue，不直接改 README，避免档案被半成品污染。
- Issue 关闭条件：内容已合并进 README 且我确认过。
- 在网页端可把 Issues 加入 **Projects** 看板（Board 视图），用于可视化进度。

**6 个待办 Issue 的正文已预置在 `tools/issues/`**，可用脚本一次性建好：

```bash
GH_TOKEN=你的令牌 python tools/create_issues.py
```

脚本幂等：已存在的同名 Issue 会跳过，可反复执行。

## 本地同步与日常维护

**首次克隆**

```bash
git clone git@github.com:2295593737/ai-personal-profile.git
cd ai-personal-profile
```

**每次修改**

```bash
git pull                                   # 先同步，避免冲突
# ...编辑 README.md 的某个章节...
git add README.md CHANGELOG.md
git commit -m "profile(沟通风格): 补充不喜欢的长篇开场"
git push
```

**约定**

- 一次提交只改一个章节，commit 前缀用 `profile(章节名):`，方便按章节筛选历史。
- 改了内容就同步补一行 CHANGELOG，否则以后回溯只能看 commit message。
- 真实隐私细节先写在 `drafts/`（已在 .gitignore 中忽略），确认可公开后再移入 README。

## 版本与追溯

- 所有修改通过 Git 提交，**任何一次变更都可追溯、可回退**。
- 建议粒度：一次提交只改一个章节，commit message 形如 `profile(沟通风格): 补充不喜欢的长篇开场`。
- 回退单次修改：`git revert <commit-sha>`
- 回退整个文件到某个历史版本：`git checkout <commit-sha> -- README.md`
- 查看某行是谁、何时改的：`git log -L <起始行>,<结束行>:README.md`
- 更完整的改动历史见 [CHANGELOG.md](CHANGELOG.md)。
